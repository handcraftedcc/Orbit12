# Module extensibility and lightweight installer

User requirement: keep adding modules straightforward; prefer installing new algorithms without rebuilding firmware if memory/performance remain suitable. Do not pretend that loading presets is loading a new algorithm. Preserve all current UI, bitmaps, fonts, navigation and behavior; extension management lives in the desktop tool, not a redesigned device UI.

## Supported baseline and explicit evaluation gate
Baseline modules are native C++ with fixed state, a descriptor, parameter/save-attribute schema and fixtures. A module author adds one directory and manifest; a registry generator supplies includes, descriptor lookup and state-union membership. No manual edits across controller, persistence, UI and registry files. The UI automatically uses existing parameter controls and layout. Examples and a `new-module` command produce a minimal compileable module and test fixture.

Adding a new native algorithm to this baseline requires relinking/reflashing firmware. The installer hides manual build steps, caches unchanged objects and can consume a compatible prebuilt UF2 containing the desired module set. This is explicitly a fallback, not fulfillment of independent runtime loading. Existing module presets/data can transfer directly without firmware changes.

Before closing the extension architecture, Sol runs E00 and submits one architectural decision report. Do not reject runtime modules by asserting unmeasured interpreter overhead. Native loadable code could run near static-code speed, but requires a relocation loader, versioned ABI, state allocation limits and safe firmware/plugin compatibility. A small interpreted runtime avoids native relocation but adds dispatch cost and runtime RAM/flash; both need measurements. Lack of an evidenced official general-purpose plugin-loader API in the reviewed Arduino-Pico documentation is a support risk, not proof it is impossible.

| Candidate | Benefits | Evidence needed |
|---|---|---|
| Static native + installer-managed firmware | Predictable state/runtime, simple build and debugging | Baseline CPU/RAM/flash and cached build/install workflow |
| Separately compiled native plugin | Potential near-native processing; independent algorithm installation | Working RP2040 relocation/code placement, bounded RAM/executable storage, stable C ABI, no cross-firmware C++ ABI dependencies, safe file/flash maintenance and compatibility rejection |
| Established small bytecode runtime | Portable algorithm packages and validation before execution | Actual supported RP2040 build, bounded arena/instruction budget, per-event timing, six-instance cost and full musical expressiveness; no custom general-purpose VM project |

E00 prototypes a trivial transpose and stateful timed delay against the native baseline. Compare target code and static RAM, six instances, event processing time, worst engine loop and UI-load MIDI jitter at 300 BPM/full swing. Host benchmarks alone do not establish RP2040 performance. Candidate gate: all architecture timing/RAM limits still hold, no allocation after instance construction, no blocking API, bounded instruction/work budget, deterministic reset/stop, source-equivalent traces, malformed/incompatible packages fail before activation. Proposed extra loader/runtime budget <=16 KiB RAM and <=256 KiB flash, subject to measured total headroom. An independently installed algorithm must run without relinking firmware to pass the defining feature check.

If no supported candidate meets these gates, document the measured failure or unresolved tooling limitation and deliver installer-managed native firmware. If hardware is unavailable, retain runtime loading as unverified rather than claiming either success or significant performance cost. Core migration and native module authoring continue while this isolated evaluation runs. Choosing a runtime or native loader is a scheduled architectural decision, not a Luna implementation choice.

## Module package contract
Native baseline (implemented): each module is a `module.json` manifest plus its C++ sources. Fields: `package_format`, `module_id` (core: plain id; user: `user.<author>.<name>`), `scene_key` (at most 10 characters, unique, the SCN1 module id; core equals `module_id`), `display_name`, `label`, `kind` (`processor` or `input`), `module_version`, `engine_api` (must equal `kEngineApi`), `descriptor`, `state` (type and bytes), `parameters` (name, type, range, default, options, saved, ui_only, global_binding), `attributes`, `header`, `sources`, `provenance` (origin, author, license) and `enabled_in_release`. `kind` is `native_source` for every module today; the other kinds in this list (`firmware_bundle`, `data`, validated runtime) are not implemented. The contract is documented for authors in `docs/modules/README.md`. Runtime loading is out of scope and no loader depends on this manifest yet. IDs and schema names are stable scene keys. All external inputs are bounded, paths relative/allowlisted, hash checked, and duplicate IDs/incompatible versions rejected. Checksums establish integrity, not publisher trust. No arbitrary installation hooks or shell evaluation. Native source builds are explicit trusted-code operations in the local build tool, never device-side compilation.

Future runtime host ABI must expose only fixed note buffers, immutable global/transport snapshots, bounded deterministic random choices, parameter values and private state storage. No direct USB, filesystem, GPIO, display, heap or arbitrary engine pointers. Use integer widths, explicit buffer capacities and API version; no C++ STL/object ABI across separately compiled packages. This constrains a future prototype without prematurely adding a loader to production firmware.

## Installer contract
Implement a small Python CLI first, with a documented one-command launcher for Windows; a large GUI/Electron app is out of scope. Commands: `devices`, `info`, `backup`, `restore`, `flash`, `modules list`, `modules install`, `new-module`. Human-friendly output must state when module installation requires a firmware update. Support local verified packages first; do not invent a hosted registry or auto-download arbitrary code.

`info` obtains firmware/API/module inventory and board identity through core-0 CDC in stopped maintenance. `backup/restore` uses the framed, checksum-verified scene/settings protocol from architecture. `flash` validates RP2040 board/family, image address ranges and partition compatibility, backs up settings/scenes, requests BOOTSEL or explains the physical action, copies verified UF2 to the identified device, waits for re-enumeration with a timeout, and verifies reported firmware/module inventory. Do not choose an arbitrary removable drive or format flash. Missing/ambiguous device is a clear error. A failed update retains the host backup with a recoverable manual UF2 procedure.

UF2 writes must not overlap the configured filesystem partition; inspect image blocks and test preservation instead of assuming a firmware update preserves scenes. Partition changes require verified backup/restore. Release downloads: the installer fetches firmware releases only from a configured GitHub repository (default `handcraftedcc/Orbit12`; `--repo` selects a fork). It reads `release-manifest.json` and `SHA256SUMS` from that release, verifies the UF2 SHA-256, size, family `0xe48bff56`, board `adafruit_macropad_rp2040`, engine API, and the image range against the filesystem partition before any flash step. Downloads are never executed and no hosted registry is used. The manifest format is defined by `tools/arduino/make_release_manifest.py` (schema 1).

Initial migration from CircuitPython imports a host backup of its userdata files. Never promise automatic recovery of overwritten CIRCUITPY data. Uploading software to a real attached board occurs only upon an explicit installer flash/install action.

`modules install` selects direct transfer for data/validated runtime packages, or resolves a compatible firmware bundle/local cached build for native algorithms, prints the planned firmware/module changes, then uses the same verified flash flow. It never calls a preset a newly installed algorithm. Tests mock discovery/CDC/BOOTSEL drives, invalid manifests/path traversal, wrong board, bad hash, incompatible API, interrupted transfer, missing re-enumeration and scene preservation. Actual flash/round-trip remains a hardware release check.

## Source basis
Arduino-Pico documents firmware update staging and LittleFS partitions, not a general plugin ABI in these pages: [OTA update mechanism](https://arduino-pico.readthedocs.io/en/latest/ota.html), [filesystem layout](https://arduino-pico.readthedocs.io/en/latest/fs.html). RP2040 documents ROM USB boot/UF2 and flash access: [RP2040 datasheet](https://datasheets.raspberrypi.com/rp2040/rp2040-datasheet.pdf). The plugin tradeoffs and budgets above are architectural proposals, not measurements established by those sources.
