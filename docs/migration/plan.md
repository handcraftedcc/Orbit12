# Dependency-ordered implementation plan

Sol coordinates and integrates; Luna implements the tasks below. Each task is a separate bounded assignment, not a request to design the application. A task may read the named Python source and existing tests but must not redesign contracts. Give each agent its task, relevant contract sections, file ownership and prerequisites; do not fork the full architecture conversation. Run at most two independent implementation agents when integration needs a slot. Sol owns `status.md` and assigns disjoint files.

For every algorithm task: port its source-declared parameters/defaults/ranges/callbacks/save_attrs, preserve queue multiplicity/ordering, include at least one normal trace plus stop/reset/overflow boundary, and run relevant native tests. `behavior-contracts.md` is the task detail index; source is the final oracle. Sol can split a task by module/file to fit agent context, but cannot silently reduce its scope. Module tests can proceed with fake ports while hardware tests are pending. E00 is an evidence gate, not permission to replace the native migration with an unmeasured runtime. See `extensions.md` for its package and installer contracts.

Scheduled architecture checkpoints: after T00/T11a feasibility (validate core/USB/flash assumptions), after first full chain plus scene round-trip (validate state ownership and memory), and before release (review consolidated evidence). Sol submits one concise report at each checkpoint; no per-module architect reviews. Within approved architecture, Sol continues ordinary implementation and test repair autonomously.
