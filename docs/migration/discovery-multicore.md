# Multicore MIDI/UI feasibility discovery

This note records the earlier feasibility exploration of an RP2040 `setup1()`/`loop1()` split. Its original preference for a single-core baseline was superseded by ADR-06, which adopts the two-core ownership split in `architecture.md` subject to T00/T11a feasibility validation. The observations and unverified risks below remain relevant to that validation. Arduino-Pico documents `setup()`/`loop()` on core 0 and `setup1()`/`loop1()` on core 1; it also warns that Arduino libraries are generally not thread-safe and that shared peripherals/memory and flash/XIP stalls remain. [Arduino-Pico multicore docs](https://arduino-pico.readthedocs.io/en/latest/multicore.html) [Pico-SDK use warning](https://arduino-pico.readthedocs.io/en/stable/sdk.html)

## What the official sources establish

- **Core and USB service:** Arduino-Pico states that core 0 normally runs the sketch, while `setup1()` and `loop1()` execute on core 1. Its multicore docs explicitly say core 0 manages USB and that idling core 0 too long can freeze USB because USB IRQs are serviced there. Adafruit TinyUSB's RP2040 port initializes TinyUSB's IRQ handler and a task runner in the context where the device is initialized, and guards `tud_task()` with a mutex. Initialize and call the chosen TinyUSB device/MIDI API only from core 0; do not move the USB object, MIDI receive/send, or service calls to core 1. [Arduino-Pico multicore docs](https://arduino-pico.readthedocs.io/en/latest/multicore.html) [Adafruit TinyUSB RP2040 implementation](https://github.com/adafruit/Adafruit_TinyUSB_Arduino/blob/master/src/arduino/ports/rp2040/Adafruit_TinyUSB_rp2040.cpp)
- **Core setup is concurrent:** `setup()` and `setup1()` start at the same time; each core enters its loop after its own setup returns. Initialization that publishes shared data must therefore have an explicit readiness handoff. [Arduino-Pico multicore docs](https://arduino-pico.readthedocs.io/en/latest/multicore.html)
- **Flash stalls:** Arduino-Pico says a core-0 LittleFS/EEPROM erase or write pauses core 1. The shared XIP/cache and on-die resource conflicts can also stall core 1 when core 0 performs unrelated work. Keep flash writes stopped/maintenance-only as already specified; do not infer that splitting cores provides uninterrupted UI/input scanning during a commit, or that core 0 USB service is unaffected by flash operations. Measure USB behavior during the actual selected LittleFS operations before making that claim. [Arduino-Pico multicore docs](https://arduino-pico.readthedocs.io/en/latest/multicore.html)
- **Synchronization:** Arduino-Pico recommends ordinary multiprocessor synchronization such as circular buffers, shared flags, and mutexes; its `rp2040.fifo.push_nb()` and `pop_nb()` APIs are the documented nonblocking software-FIFO options. The board-specific FIFO is 32-bit per item and should not be used with blocking `push()`/`pop()` in the performance path. `volatile` alone is not C++ inter-thread synchronization. [Arduino-Pico multicore communication docs](https://arduino-pico.readthedocs.io/en/latest/multicore.html)
- **Peripheral ownership:** Arduino-Pico warns that Arduino functions/libraries are generally not multicore or multithread safe; calls to a given library should stay on one execution context. Treat display SPI, NeoPixel/PIO setup and updates, GPIO scanning, and each adapter object as exclusively owned by core 1 if adopting this split. Do not share an `SPI` or pixel object between cores. The SH1106 is hardware SPI and NeoPixels are a separate output, so they do not require core 0 ownership; however, library setup and hardware access on core 1 need a board build and device test. [Arduino-Pico multicore docs](https://arduino-pico.readthedocs.io/en/latest/multicore.html) [Adafruit MacroPad pinouts](https://learn.adafruit.com/adafruit-macropad-rp2040/pinouts)

## Candidate division of work

If the user wants a prototype of the split, keep all musical state and USB MIDI on core 0 and make core 1 a hardware-facing input/renderer worker:

| Core 0 (`setup()` / `loop()`) | Core 1 (`setup1()` / `loop1()`) |
| --- | --- |
| Initialize USB device and MIDI; own all TinyUSB service and send/receive calls | After a nonblocking ready handshake, initialize and own the SH1106/SPI and NeoPixel adapter objects |
| Own transport, scheduler, input/processor chain, note state, release safety, output queues, controller actions, persistence state | Scan GPIO keys/encoder/switch at the required cadence; publish raw bounded input records to core 0 |
| Consume raw input records; decide UI shortcuts versus musical events; update a bounded immutable UI snapshot | Read a versioned/immutable UI snapshot and render dirty regions; update pixel hardware from published colors |
| Handle all note output and transport clock on the existing bounded schedule | Never send MIDI, mutate musical/module/scene state, or access filesystem |

This keeps display transfers and UI composition out of the MIDI processing loop. Core 0 remains the only owner of MIDI and the app's domain/controller state, avoiding a cross-core move of the complex chain. Core 1 does physical sampling and drawing only. The proposal requires a departure from the current single-core architecture's polling-order contract and thus should be introduced as an explicit, measured architecture decision, not smuggled in as an adapter detail.

## Cross-core queue shape and failure rules

Use two independent bounded channels: an input-to-core-0 stream for physical edges/encoder changes, and a core-0-to-core-1 latest-state mailbox for the render model. Keep producer and consumer ownership explicit. For a custom SPSC ring, only the producer writes `head`, only the consumer writes `tail`, and publish the payload before the index with release semantics; consume the index with acquire semantics before reading the payload. Use fixed-size events, no allocation, no mutex, no waiting, and a counter on full. Add a compile-time lock-free check for the exact atomic index type and inspect/build-test its RP2040 implementation: do not assume `std::atomic<uint32_t>` is lock-free or bounded on Cortex-M0+. If that check fails, evaluate Arduino-Pico's documented nonblocking 32-bit FIFO for packed event records or a short, explicitly bounded platform primitive; do not replace atomics with `volatile` or a blocking mutex in the MIDI loop. Run a cross-core stress test with wraparound and queue saturation before accepting either implementation. [Arduino-Pico multicore communication docs](https://arduino-pico.readthedocs.io/en/latest/multicore.html)

Input queue overflow is a musical safety failure, not a dropped-event statistic alone. Core 0 must stop accepting new note-ons, reconcile currently held physical keys or enter a bounded panic/release path, and expose a diagnostic. Encoder movement may be coalesced into a saturating delta; key edges may not be silently coalesced if a press and release pair changes musical state. The render side can safely skip intermediate snapshots and draw the newest complete version. No renderer callback may mutate live domain state.

The FIFO APIs are documented as nonblocking only in their `_nb` forms; official docs do not establish their capacity or latency for the desired event workload. The docs also say the hardware FIFO itself is occupied by core pause/resume mechanisms on RP2040. Check the selected core version's implementation before using the software FIFO in a sustained event stream. A custom SPSC queue has more capacity control, but its atomic lowering and latency still require compiler inspection and measurement.

## Tradeoffs and alternative

**Potential gain:** UI rendering or an unusually expensive screen rebuild no longer consumes core-0 instructions in the same loop as MIDI scheduling. Input scanning also proceeds independently while core 0 works.

**Costs and risks:** The design adds concurrent startup, queue overflow/recovery, memory ordering, separate 4 KiB stacks by default, cache/bus contention, and more difficult debugging. Arduino-Pico documents that the normal 8 KiB stack is split into 4 KiB per core when multicore is enabled; `core1_separate_stack = true` gives each core its own 8 KiB stack but consumes more RAM. The core also documents no background work/interrupts on core 1 by default (apart from optional/needed system tick behavior); don't move ISR assumptions with the UI. [Arduino-Pico stack/core-1 docs](https://arduino-pico.readthedocs.io/en/latest/multicore.html)

**Alternative considered, not selected:** Keep the application single-core and profile dirty-driven, chunked OLED updates on core 0. This would preserve simple ordering, but ADR-06 selects the two-core split because the user requested MIDI/UI isolation. If T00/T11a evidence shows the split cannot meet its bounded synchronization and ownership requirements, report that evidence and compare this alternative through the documented escalation process.

## Verified versus pending

Verified from official docs/source: Arduino-Pico's core-1 entry points and concurrent setup behavior; core 0's USB responsibility; core-0 flash-write pause of core 1; 4 KiB default stack split; documented FIFO APIs; general library thread-safety caution; and TinyUSB's RP2040 IRQ/task mechanism. Not established without firmware and hardware: current Arduino-Pico/TinyUSB ISR routing under the exact pinned core profile, worst-case MIDI jitter under concurrent SPI/PIO display/LED work, USB service latency during LittleFS writes, actual atomic lock-freedom/code generation, event FIFO sizing/throughput, input cadence under core-1 load, and whether the two-core implementation improves MIDI timing enough to justify its complexity.
